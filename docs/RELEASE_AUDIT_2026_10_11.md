### Final approval-decision correction

SEC-10: HTTP rejection previously returned success while an approval was waiting on its target, and terminal proposals also returned false rejection success. Both decisions now share a proposal lock; rejection checks current staff ownership/Owner authority, writes an audit event and returns 409 for terminal proposals. Approval additionally changes PENDING status conditionally, so a legacy/uncoordinated rejection cannot be overwritten. Deterministic HTTP/database regressions reproduced the former behavior and cover both winner orders and terminal/boundary cases. Success remains `{rejected: true}`.

## Final interrupted-workflow review

- **UX-03 — duplicate Direct Sales orders:** a real local save committed with HTTP 201, its response was dropped, and refreshing the quote then confirming created a second order. The page now retains the exact request/key, locks edits and provides an explicit status check. Recovery retains the original attempt through HTTP 429; a definitive initial stale-quote refusal still permits correction. Recovery is held only in page memory; an unresolved attempt requires reconciliation against existing orders before starting another.
- **UX-04 — stale staff decisions:** both an actual approval and an actual rejection committed while their dropped responses left the page showing PENDING. Those two controls now perform a read-only refresh on failure and stay disabled during reconciliation. No mutation is automatically replayed. A request that never reached the server remains pending and retryable.
- **UX-05 — duplicate customer return intent:** an actual HTTP 201 followed by a lost response and unchanged resubmission created two requests against a fulfilled quantity of two. The customer form now uses exact-payload idempotency with explicit recovery; current ownership is checked before replay and distinct intents retain quantity checks. The optional header preserves compatibility for older unkeyed API callers, whose requests remain non-idempotent. No migration or refund behavior changes.
- **UX-06 — misleading missing-order errors:** catch-all error handling turned transient order reads into 404 pages. Only the domain's explicit 404 now reaches the not-found boundary; unexpected failures reach the existing retry boundary. Six previously failing page-load cases now pass within nine boundary regressions, including unauthorized access.
- **ADMIN-03 — unavailable order actions:** seven incorrect controls appeared across expired, cancelled, partially shipped and fully shipped order cases. Shipment, cancellation and payment forms now use the same existing status/quantity conditions as the domains, while retaining their independent permissions. A browser matrix covers eight order states plus Support/Sales boundaries; no business policy changes.
